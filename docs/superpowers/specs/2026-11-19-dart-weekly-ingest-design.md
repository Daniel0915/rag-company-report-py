# DART 전 유형 수집 + 주간 자동 수집 설계

작성일: 2026-11-19 · 대상 저장소: `rag-company-report-py`

## 왜 만드나

챗봇이 **최신 실적과 주요 결정 사항을 정확히 답하게** 하려는 것이 목적이다. 지금은 정기공시(A)와 지분공시(D)만 수집하고, 관리자가 버튼을 눌러야 새 공시가 들어온다.

- **최신 실적:** 분기 보고서(A)보다 한 달쯤 먼저 나오는 거래소공시(I)의 "영업(잠정)실적"이 필요하다.
- **주요 결정:** 주요사항보고(B, 자기주식·유상증자·합병 결정)와 거래소공시(I, 공정공시)가 필요하다. 발행공시(C)와 기타공시(E)는 그 후속 문서다.

이 작업은 세 단계 중 첫 번째다.
1. **수집 확장 + 주간 자동 수집** (이 문서)
2. RAG 답변 평가(`2026-11-19-rag-eval-design.md`, 설계 중)
3. 검색 개선: 최신 공시 우선, 질문 종류별 공시 유형 우선

수집이 먼저인 이유는 평가 질문과 검색 개선 모두 이 데이터가 있어야 하기 때문이다.

## 목표, 비목표, 반목표

**목표**
1. 워치리스트 22곳의 DART 공시를 A~J 전 유형으로 수집해 기존 기업별 벡터 인덱스와 공시 그래프에 넣는다.
2. 처음에 최근 2년치를 한 번 채우고(backfill), 그 뒤로는 **매주 토요일 07:10**에 새 공시만 자동으로 수집한다(사용자 결정).
3. 이미 색인한 공시는 **다운로드 전에** 건너뛴다.
4. 실행이 실패하거나 일부 공시가 실패하면 macOS 알림으로 알린다. 자세한 내용은 날짜별 로그에 남긴다.

**비목표**
- 검색 방식 변경(최신 우선, 유형 우선). 3단계 작업이다.
- 뉴스 자동 수집. 지금처럼 관리자 버튼으로 수집한다.
- 클라우드 배포, 클라우드 DB.
- DART 구조화 API(재무정보 등) 수집.

**반목표** (돌아가도 실패로 보는 경우)
- 이미 있는 공시를 다시 넣어 **청크가 중복**되는 것
- 실패했는데 아무 알림 없이 조용히 넘어가는 것
- 기존 채팅·관리자 API의 동작이 깨지는 것
- 이미 받은 공시를 매번 다시 다운로드해 DART 하루 호출 한도를 낭비하는 것

## 현재 상태 (2026-11-19 확인)

- `DISCLOSURE_TYPES = ["A", "D"]` (`app/services/company_report_index.py:27`)
- 공시 하나를 처리하는 순서: 그래프에 `Report` 기록 → 원문 zip 다운로드 → 파일별 MD5 해시를 기록 파일(`data/company-report-index.json`)과 비교 → 바뀐 파일만 청킹·임베딩 → 기록 파일 저장. 이미 있는 공시도 **다운로드는 매번** 일어난다.
- **이 저장소의 `data/`에는 그 기록 파일이 없다.** 지금 Neo4j 데이터는 Spring 프로젝트가 넣은 것이고, 기록 파일은 `../rag-company-report/data/company-report-index.json`(4,925건, 같은 형식)에만 있다. Neo4j의 `Report` 노드는 4,922개다. 기록 파일 없이 수집을 돌리면 모든 공시를 새로 넣어 청크가 중복된다.
- `/api/company-report/index`는 프로세스 안의 `threading.Lock`만 쓴다. 배치 프로세스와 API 서버가 동시에 색인하는 것은 막지 못한다.
- 22곳 × 최근 2년 공시 수:

  | 유형 | A | B | C | D | E | F | G | H | I | J |
  |---|---|---|---|---|---|---|---|---|---|---|
  | 건수 | 206 | 214 | 343 | 6,693 | 255 | 0 | 0 | 0 | 2,792 | 746 |

- B, C, E, I, J 원문을 유형별로 몇 건씩 받아 기존 `DartXmlDocumentReader`로 읽어 봤다. 모두 오류 없이 섹션 1~9개, 청크 2~14개로 나뉘었다.
- 이 Mac(M1)에서 bge-m3 임베딩 속도는 초당 약 3.7청크다. 새로 넣을 청크는 약 11만 개로 추정되고, backfill에 약 8시간이 걸린다. 대부분은 새 14곳의 정기공시다.

## 수집 주체

**공시 수집은 이 파이썬 프로젝트에서만 한다**(사용자 결정). 원 Spring 프로젝트(`../rag-company-report`)도 같은 Neo4j를 쓰지만, 기록 파일을 따로 갖고 있어 수집하면 청크가 중복된다. 그래서 Spring 쪽 기록 파일은 처음에 한 번 가져오는 데만 쓰고, Spring 앱의 수집 기능은 더 쓰지 않는다. README의 "참고"에 이 내용을 적는다.

## 접근 방식

| 결정 | 고려한 방식 | 선택과 이유 |
|---|---|---|
| 실행 주체 | **A. macOS launchd** / B. Claude Code 세션 예약 / C. Claude 클라우드 예약 + 클라우드 DB | **A** (사용자 선택). 수집에는 LLM이 필요 없다. B는 세션이 열려 있을 때만 돌고 7일 뒤 사라지며, 실행마다 구독 사용량을 쓴다. C는 클라우드에서 이 Mac의 `localhost` Neo4j와 Ollama에 접근할 수 없어 DB 이전이 필요하다. |
| 이미 받은 공시 판단 | 원문 해시 비교(지금 방식) / **접수번호 기록으로 다운로드 전 건너뛰기** | **접수번호 기록**. 사용자 요구("이미 데이터가 있으면 수집 안 해도 됨")와 DART 호출 한도 때문이다. 정정 공시는 새 접수번호로 나오므로 놓치지 않는다. |
| 알림 | **macOS 알림 + 로그 파일** / 이메일·슬랙 | **macOS 알림**. 별도 계정이나 키가 필요 없다. 전부 성공한 날은 알리지 않는다. |

## 설계

### 수집 명령

```bash
python -m app.ingest backfill [--since 2024-11-19] [--corp 00126380 ...] [--types A,B,...]
python -m app.ingest update
python -m app.ingest status      # 마지막 실행 결과, 대기 중인 실패 공시 수 출력
```

- `backfill`: 기간(기본: 오늘부터 2년 전까지) 안의 공시를 모두 수집한다. 처음 한 번 수동으로 돌린다. 중간에 멈춰도 다시 실행하면 이어서 한다.
- `update`: launchd가 매주 토요일 실행한다. 조회 기간은 **마지막 성공 실행일 7일 전부터 오늘까지**다(평소 약 2주). 한동안 Mac이 꺼져 있었으면 그만큼 기간이 자동으로 넓어진다. 7일을 겹치는 이유는 접수일 기준 목록에 늦게 반영되는 공시를 놓치지 않기 위해서다(설계자 판단).
- `--corp`, `--types`로 범위를 좁힐 수 있다. 기본값은 워치리스트 22곳 × A~J 전 유형이다. F, G, H는 지금 0건이지만 목록 조회 비용이 작아서 그대로 포함한다.
- 기존 `/api/company-report/index` 엔드포인트는 화면의 "최신 공시 가져오기" 버튼이 부른다(`frontend/src/api.ts:95`, 원 프로젝트). 같은 서비스, 같은 건너뛰기 규칙, 같은 잠금과 상태 파일을 쓴다(설계자 판단).
  - 기간을 주지 않으면 `update`와 똑같이 동작한다. 지금의 "최근 2년" 기본값은 없앤다. 버튼을 눌렀을 때 몇 시간짜리 요청이 되는 것을 막기 위해서다.
  - 기간을 주면 그 기간에 대해 `backfill`처럼 동작한다.
  - 응답 형식은 바꾸지 않는다.

### 이미 받은 공시 건너뛰기

- 기존 기록 파일(`data/company-report-index.json`, 키 `접수번호/파일명`)을 그대로 쓴다. **접수번호의 파일 키가 하나라도 있으면 그 공시는 다운로드하지 않고 건너뛴다.**
- 원문을 받았는데 청크가 0개인 공시(빈 문서)도 기록 파일에 빈 청크 목록으로 남긴다. 그래야 매번 다시 받지 않는다. 지금은 청크가 0개면 기록 파일을 저장하지 않는다.
- 그래프 `Report` 기록(`record_disclosure`)은 `MERGE`라 몇 번 실행해도 결과가 같다. 건너뛰는 공시도 그래프 기록은 지금처럼 한다(설계자 판단: 호출 비용이 작고 그래프 누락을 메운다).
- **최초 1회 이전:** 이 저장소의 `data/`에 기록 파일이 없고 Spring 프로젝트에 있으면, `python -m app.ingest import-ledger ../rag-company-report/data/company-report-index.json`으로 가져온다. 가져온 뒤에는 기록 파일의 접수번호 수와 Neo4j 공시 청크의 고유 접수번호 수를 비교해 출력한다. 수집 명령은 기록 파일이 비어 있는데 Neo4j에 공시 청크가 있으면 **실행을 거부**하고 이전 명령을 안내한다. 중복 적재를 구조적으로 막기 위해서다.
  - 2026-11-19 확인: Spring 기록 파일의 청크 ID 78,348개가 모두 Neo4j에 있고, 기록 파일에 없는 공시 청크는 없다.
  - 뉴스 청크(`doc_type=NEWS`)도 `metadata.rcept_no`를 갖고 있다(702개). 위 비교와 거부 조건에서는 뉴스 청크를 뺀다.
- **기록 파일은 잠금을 잡은 뒤에 다시 읽는다.** API 서버는 시작할 때 한 번 읽고 저장할 때 파일 전체를 덮어쓴다. 그래서 배치가 추가한 항목을 서버가 덮어쓰지 않도록, 색인 작업마다 잠금을 잡은 직후 파일을 다시 읽는다.

### 정정 공시

`[기재정정]` 같은 정정 공시가 나오면 원본 공시와 정정본이 둘 다 검색에 남는다. 그러면 챗봇이 정정 전 숫자를 인용할 수 있다. 이번 단계에서는 **원본을 지우지 않고 관계만 기록한다**(설계자 판단).
- 정정 공시(`report_nm`이 `[기재정정]` 등 대괄호 접두어로 시작)를 처리할 때, 같은 기업에서 접두어를 뗀 이름이 같은 이전 공시를 찾아 그래프에 `(정정본:Report)-[:CORRECTS]->(원본:Report)`를 기록한다. 원본을 못 찾으면 기록만 건너뛴다.
- 정정본 청크에는 `metadata.corrects_rcept_no`를 붙인다.
- 원본 청크를 검색에서 빼거나 정정본을 우선하는 것은 3단계(검색 개선)에서 이 기록을 이용해 처리한다. 지우는 작업은 되돌리기 어렵고, 정정본이 원본의 일부만 담는 경우도 있기 때문이다.

### 실패 처리와 상태 파일

- 상태 파일 `data/ingest-state.json`에 남기는 것: 마지막 실행 시각, 마지막 성공 실행일, 실패해서 다시 시도할 공시 목록(접수번호, 기업, 유형, 오류 요약, 시도 횟수).
- 공시 하나가 실패해도 실행을 멈추지 않는다. 실패한 공시는 기록 파일에 넣지 않고 상태 파일의 재시도 목록에 넣는다. 다음 `update`가 조회 기간과 상관없이 이 목록을 먼저 다시 시도한다. 5번 실패한 공시는 재시도를 멈추고 알림과 `status`에 표시한다.
- **실행 전 점검:** Neo4j 연결, Ollama 임베딩 모델 응답, DART 키 유효성(목록 조회 1회)을 확인한다. 하나라도 실패하면 아무것도 하지 않고 실패 알림을 띄운 뒤 종료한다.
- **DART 하루 호출 한도 초과:** DART 응답 상태가 한도 초과면 즉시 멈추고, 남은 작업은 다음 실행으로 넘기고, 알림을 띄운다. 정확한 한도와 상태 코드는 구현 시 DART 개발 가이드에서 확인한다.
- 같은 시각에 두 번 돌지 않도록 `data/ingest.lock` 파일 잠금을 쓴다. 배치와 `/api/company-report/index`가 같은 잠금을 쓴다. 잠금을 못 잡으면 배치는 "이미 실행 중"을 로그에 남기고 종료하고, API는 409를 돌려준다.

### 알림과 로그

| 상황 | macOS 알림 |
|---|---|
| 실행 전 점검 실패, DART 한도 초과, 예상하지 못한 예외 | "공시 수집 실패: <원인 한 줄>" |
| 일부 공시 실패 | "공시 수집 완료: 신규 N건, 실패 M건" |
| 전부 성공 | 알림 없음 |

- 알림은 `osascript -e 'display notification ...'`로 띄운다. 알림을 띄우는 데 실패해도 수집 결과에는 영향이 없다.
- 로그는 `logs/ingest/YYYY-MM-DD.log`에 남긴다. 내용은 점검 결과, 기업·유형별 조회 건수, 공시별 결과(신규·건너뜀·실패와 청크 수), 소요 시간이다. 30일이 지난 로그는 지운다. `logs/`는 `.gitignore`에 추가한다.

### launchd 설정

- 사용자 LaunchAgent: `~/Library/LaunchAgents/com.daniel0915.rag-company-report.ingest.plist`
- **매주 토요일 07:10**에 프로젝트 폴더에서 `.venv/bin/python -m app.ingest update`를 실행한다(사용자 결정). Mac이 잠자고 있었으면 깨어난 뒤 실행되고, 꺼져 있었으면 다음 주 실행 때 조회 기간이 넓어져 메워진다.
- 저장소에 plist 템플릿과 `scripts/launchd/install.sh`, `scripts/launchd/uninstall.sh`를 둔다. 설치 스크립트가 템플릿의 프로젝트 경로를 채워 넣고 `launchctl`로 등록한다.
- 전제 조건(README에 적는다):
  - Docker Desktop과 Ollama가 로그인할 때 자동으로 실행되도록 설정
  - Neo4j 컨테이너가 Docker와 함께 켜지도록 `docker update --restart unless-stopped company-report-neo4j`

### 처음 실행 순서

1. `python -m app.ingest import-ledger ../rag-company-report/data/company-report-index.json`
2. `caffeinate -i python -m app.ingest backfill`로 밤사이 실행한다. 약 8시간 걸리고, 잠자기 모드 때문에 멈추지 않게 `caffeinate`를 쓴다.
3. `python -m app.ingest status`로 결과를 확인한다.
4. `scripts/launchd/install.sh`로 주간 수집을 등록한다.

## 파일 배치

```
app/ingest/
  __main__.py          # backfill / update / status / import-ledger 하위 명령
  runner.py            # 기간 계산, 재시도 목록 처리, 실행 요약
  state.py             # ingest-state.json 읽기/쓰기
  preflight.py         # Neo4j·Ollama·DART 점검
  notify.py            # macOS 알림
  lock.py              # 파일 잠금
app/services/company_report_index.py   # 유형 목록 확장, 접수번호 건너뛰기, 빈 문서 기록, 범위 인자
app/routers/company_report.py          # 파일 잠금 공유, 잠금 실패 시 409
scripts/launchd/                       # plist 템플릿, install.sh, uninstall.sh
tests/test_ingest_*.py                 # 기간 계산, 건너뛰기, 재시도, 상태 파일, 잠금
```

## 완료 기준

1. 기록 파일을 가져온 뒤 삼성전자 하나로 `backfill --corp 00126380`을 돌렸을 때, 기록 파일에 있는 공시는 다운로드 없이 건너뛴다. 새로 들어가는 것은 B·C·E·I·J와, 기존 데이터의 마지막 날짜(2026-08-31) 이후에 나온 A·D 공시다. 실행 전후 삼성전자 청크 수의 차이가 새로 들어간 청크 수와 같다(중복 없음).
2. 같은 명령을 한 번 더 돌리면 신규 0건이다.
3. Neo4j를 끈 상태에서 `update`를 돌리면 실패 알림이 뜨고 아무것도 바뀌지 않는다.
4. 전체 `backfill`이 끝난 뒤 22곳 모두 정기공시가 있다.
5. launchd 등록 후 첫 토요일 실행에서 로그 파일이 생기고 `status`에 실행 기록이 남는다.
